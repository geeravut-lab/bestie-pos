# Knowledge: การโอนและรับ Crypto ระหว่างกัน (สำหรับ Bestie POS)

ข้อมูล ณ วันที่ 18 พ.ย. 2569 · สรุปจากการค้นคว้าและถาม-ตอบใน session ออกแบบ Bestie POS
เอกสารนี้ไม่ใช่คำแนะนำทางกฎหมาย ต้องให้ทนายด้าน fintech ยืนยันก่อนใช้งานจริง

---

## 1. สรุปสั้น

- **ทางเทคนิค:** การรับ crypto โดยให้ลูกค้าสแกน QR แล้วโอนเข้ากระเป๋าของเรา จากนั้นตรวจบนบล็อกเชนว่าเงินเข้าแล้ว **ทำได้จริง**
- **ข้อเข้าใจผิดที่ต้องแก้:** ฝ่ายรับ **หยุดหรือปฏิเสธการโอนก่อนเงินเข้าไม่ได้** เพราะฝ่ายโอนเป็นคนส่งธุรกรรมขึ้นบล็อกเชนเอง ฝ่ายรับตรวจได้หลังเงินเข้าแล้วเท่านั้น จึงต้องป้องกันความผิดพลาดตั้งแต่ตอนสร้าง QR
- **ทางกฎหมาย:** ร้านรับ crypto เองภายใต้สัญญาระหว่างคู่สัญญาทำได้ แต่มีภาระตามกฎหมายฟอกเงินและภาษี และ ธปท. ไม่สนับสนุน
- **การตัดสินใจใน Bestie POS:** crypto ไม่เป็นช่องทางจ่ายบิลโดยตรง แต่ใช้ **เติม Bestie Credit** (กระเป๋าเงินบาทแบบเติมล่วงหน้า) ผ่านโมดูลที่ปิดไว้จนกว่าทนายยืนยัน

---

## 3. Flow การโอน-รับ: สิ่งที่ถามและคำตอบ

### ขั้นที่ 1 — เครื่องฝ่ายรับแสดง QR ของ address
**ถูกต้อง แต่ควรเปลี่ยนเป็น "ใบเรียกเก็บเงิน" (payment request)**
- QR ควรมีข้อมูลครบทั้ง **เหรียญ + เครือข่าย + จำนวนเงิน + address** แอปกระเป๋าเงินจะได้เติมให้เอง ฝ่ายโอนไม่ต้องพิมพ์จำนวน
- มาตรฐาน QR:
  - **BTC:** BIP21 เช่น `bitcoin:<address>?amount=<btc>`
  - **ETH / ERC-20:** EIP-681 เช่น `ethereum:<contract>@1/transfer?address=<ผู้รับ>&uint256=<จำนวนหน่วยย่อย>`
  - **Tron:** ไม่มีมาตรฐานที่ทุกแอปรองรับ ให้ใส่แค่ address ใน QR และแสดงจำนวนเงินตัวใหญ่พร้อมปุ่ม copy
- **USDT มีหลายเครือข่าย** เช่น Ethereum (ERC-20), Tron (TRC-20), BNB Chain (BEP-20) และ Solana การโอนผิดเครือข่ายเป็นความผิดพลาดที่พบบ่อยที่สุด ต้องระบุเครือข่ายเป็นคำพูดข้าง QR ทุกครั้ง เช่น "USDT on TRON (TRC-20)"
- **Hardware wallet:** private key อยู่ในอุปกรณ์เท่านั้น เครื่อง POS ใช้แค่ address สาธารณะ ถ้าใช้ BTC ใช้ xpub แบบ watch-only เพื่อสร้าง address ใหม่ต่อออเดอร์

### ขั้นที่ 2 — เครื่องฝ่ายโอนสแกน ใส่จำนวน แล้วกดโอน
**ถูกต้อง** แต่ควรให้ QR กำหนดจำนวนแทนการให้ลูกค้าพิมพ์เอง
- ฝ่ายโอนต้องมีเหรียญหลักของเครือข่ายไว้จ่ายค่าธรรมเนียม (gas) เช่น โอน USDT บน Tron ต้องมี TRX และโอน USDT บน Ethereum ต้องมี ETH
- ค่า gas บน Ethereum มักแพงกว่า Tron มาก จึงแนะนำ Tron สำหรับยอดเล็ก
- ถ้าลูกค้าถอนจาก exchange โดยตรง ธุรกรรมจะมาจาก address ของ exchange ไม่ใช่กระเป๋าส่วนตัว ต้องจับคู่ด้วยจำนวนเงินเฉพาะหรือ address เฉพาะของออเดอร์แทน

### ขั้นที่ 3 — ฝ่ายรับตรวจประเภทเหรียญ ถ้าไม่ตรงให้หยุด
**หยุดไม่ได้ แต่ตรวจและแจ้งเตือนหลังเงินเข้าได้**
- ระบบเฝ้าดู address ของเราบนเครือข่ายที่รองรับ เช่น ฟัง event `Transfer` ของสัญญา USDT แล้วเทียบกับใบเรียกเก็บเงิน
- ถ้าเหรียญหรือเครือข่ายไม่ตรง ให้ส่งเข้าคิวตรวจ (review) ไม่เติมเครดิตอัตโนมัติ
- โอนผิดเครือข่ายตระกูล EVM เช่น USDT บน BNB Chain เข้า address ของ Ethereum: เงินมักกู้คืนได้ เพราะ address เดียวกันใช้ได้ทุก EVM chain ถ้าเราถือ private key เอง
- BTC ส่งไป address ของ ETH ไม่ได้ เพราะแอปกระเป๋าเงินจะปฏิเสธรูปแบบ address
- **การแสดงยอดเป็นบาทหรือ USD:** ดึงราคาจาก 2 แหล่งมาเทียบกัน แล้ว **ล็อกเรตไว้ในใบเรียกเก็บเงินพร้อมเวลาหมดอายุ** (stablecoin 15 นาที, BTC/ETH 10 นาที) เพราะ BTC และ ETH ขยับเร็ว ส่วน stablecoin คิดประมาณ 1 USD
- ต้องรองรับกรณีจ่ายขาด จ่ายเกิน และจ่ายหลังหมดเวลา

### ขั้นที่ 4 — ตรวจบนบล็อกเชนว่าธุรกรรมสำเร็จหรือยัง
**ทำได้** ผ่าน API ของผู้ให้บริการข้อมูลบล็อกเชน หรือรัน node เอง
- กำหนดจำนวน confirmation ขั้นต่ำต่อเครือข่าย (เวลาเป็นค่าโดยประมาณ):

| เครือข่าย | เวลาต่อบล็อก | ค่าที่ตั้งใน Bestie | หมายเหตุ |
|---|---|---|---|
| Tron | ~3 วินาที | 20 บล็อก (~1 นาที) | เหมาะกับการเติม USDT หน้าร้านที่สุด |
| Ethereum | ~12 วินาที | 12 บล็อก | กว่าจะ final ราว 13 นาที |
| Bitcoin | ~10 นาที | 2 confirmations | ช้าเกินไปสำหรับหน้าร้าน ถ้าจะใช้ต้องพิจารณา Lightning Network |

- บน Ethereum ต้องเช็กว่า receipt มี `status = 1` เพราะธุรกรรมที่ revert จะไม่มีเงินเข้า
- ต้องรองรับ reorg คือบล็อกถูกย้อน ด้วยการรอให้ครบจำนวน confirmation ก่อนเติมเครดิต

## 4. การจับคู่เงินที่เข้ากับบิล

- **v1 (Tron/Ethereum):** ใช้ address เดียวต่อเครือข่าย แล้วเติม **เลขท้ายเฉพาะ** ลงในจำนวนเงินของแต่ละใบเรียกเก็บ เช่น 28.45 → `28.450317` USDT ทำให้รู้ว่าเงินก้อนไหนเป็นของบิลไหน และไม่ต้องกระจายเงินไปหลาย address ซึ่งต้องจ่าย gas ทุก address
- **v2 (BTC):** สร้าง address ใหม่ต่อใบเรียกเก็บจาก xpub (BIP84) แบบ watch-only
- คีย์จับคู่: เครือข่าย + address ผู้รับ + เหรียญ + จำนวนหน่วยย่อย ภายในช่วงเวลาของใบเรียกเก็บ
- ยอมให้คลาดเคลื่อนได้เล็กน้อย (ค่าเริ่มต้นไม่เกิน 0.5% หรือ 0.10 USDT แล้วแต่ค่าไหนน้อยกว่า)
- ธุรกรรมหนึ่งจับคู่ได้กับใบเรียกเก็บเดียว และการเติมเครดิตต้อง idempotent คือเรียกซ้ำแล้วไม่เติมซ้ำ

## 5. ความปลอดภัย

- **ไม่มี private key ในระบบ POS, Firebase หรืออุปกรณ์หน้าร้านเลย** key อยู่ใน hardware wallet ของบริษัทเท่านั้น
- **Address poisoning:** ผู้โจมตีส่งเงินจำนวนเล็กมากจาก address ที่หน้าตาคล้ายของเรา หวังให้คน copy ผิด
  - ไม่สนใจธุรกรรมยอดเล็กมาก (dust) ตอนจับคู่
  - ห้าม copy address จากประวัติธุรกรรมไปใช้คืนเงิน
  - ตรวจ address ทั้งเส้นทุกครั้ง
- **ป้องกัน address ที่แสดงถูกแก้:** server ส่ง address มาพร้อมใบเรียกเก็บทุกครั้ง และหน้าจอแสดงตัวอักษร 6 ตัวแรกและ 6 ตัวท้ายตัวใหญ่ ให้พนักงานเทียบกับการ์ดที่พิมพ์ติดไว้หน้าร้าน
- **เปลี่ยน address รับเงิน:** ต้องให้ 2 คนอนุมัติ และบันทึกใน audit log
- **ตรวจ address ผู้โอนทุกครั้ง:** เทียบกับ blocklist ของเรา, รายชื่อ address ที่ติดมาตรการคว่ำบาตร และสถานะถูกระงับใน contract ของ USDT

## 6. การตัดสินใจที่ใช้ใน Bestie POS (18 พ.ย. 2569)

| เรื่อง | ตัดสินใจ |
|---|---|
| บทบาทของ crypto | ใช้เติม **Bestie Credit** เท่านั้น ไม่เป็นช่องทางจ่ายบิลโดยตรง และไม่คืนเป็นเงินสด |
| การเปิดโมดูล | ปิดไว้ก่อน เปิดได้เมื่อมีเอกสารที่ทนายยืนยัน (`legalSignOff.cryptoTopup`) ระบบเช็กที่ฝั่ง server |
| เหรียญ v1 | **USDT บน Tron (TRC-20)** และ **USDT บน Ethereum (ERC-20)** ส่วน USDC, BTC และ ETH ไว้ภายหลัง |
| ผู้ให้บริการข้อมูลบล็อกเชน | **TronGrid** สำหรับ Tron และ **Alchemy หรือ Etherscan** สำหรับ Ethereum ส่วน BTC ใช้ mempool.space ใน v2 |
| แหล่งราคา | ticker สาธารณะของ exchange ไทย (คู่เงินบาท) + CoinGecko เป็นสำรอง ถ้าสองแหล่งต่างกันเกิน 1.5% ไม่ออกใบเรียกเก็บ |
| ยอดเติมขั้นต่ำ | 500 บาทบน Tron และ 1,000 บาทบน Ethereum |
| เครดิตคงเหลือสูงสุด | 100,000 บาทต่อคน นับเฉพาะเครดิตที่เติมด้วย crypto |

### ระดับการยืนยันตัวตน (KYC) และวงเงิน — รอทนายยืนยัน

| ระดับ | ต้องยืนยันอะไร | ต่อครั้ง | ต่อวัน | ต่อ 30 วัน |
|---|---|---|---|---|
| T1 พื้นฐาน | พาสปอร์ต + ชื่อ + สัญชาติ + เบอร์โทรหรืออีเมล + ตรวจ address ผู้โอน | 500–30,000 | 30,000 | 50,000 |
| T2 เข้มข้น | T1 + พิสูจน์ความเป็นเจ้าของกระเป๋า + แจ้งที่มาของเงิน + ตรวจความเสี่ยงบล็อกเชน + เจ้าของร้านอนุมัติ | ≤100,000 | 100,000 | 500,000 |
| เกิน T2 | ไม่รับ | — | — | — |

- ไม่มีการเติมแบบไม่ระบุตัวตน
- **พิสูจน์ความเป็นเจ้าของกระเป๋า** ทำได้ 2 วิธี: ให้ลูกค้าเซ็นข้อความ (signed message) ที่ระบบส่งให้ หรือให้โอนยอดเล็กตามจำนวนที่ระบบกำหนดจาก address นั้นก่อน
- **ระบบติดธงให้ตรวจอัตโนมัติเมื่อ:**
  - เติมเกิน 3 ครั้งใน 24 ชั่วโมง
  - เติมยอดเฉียดวงเงินซ้ำๆ
  - address เดียวถูกใช้โดยลูกค้าหลายคน
  - ลูกค้าคนเดียวใช้เกิน 3 address ใน 30 วัน
- เก็บข้อมูลอย่างน้อย 5 ปี

## 7. คำศัพท์

| คำ | ความหมาย |
|---|---|
| Address | เลขกระเป๋าสาธารณะที่ใช้รับเงิน บอกคนอื่นได้ |
| Private key | กุญแจลับที่ใช้สั่งโอนเงินออก ห้ามอยู่ในระบบ POS |
| xpub | กุญแจสาธารณะแม่ ใช้สร้าง address ใหม่ได้หลายอันแบบดูอย่างเดียว (watch-only) |
| Chain / Network | เครือข่ายบล็อกเชน เช่น Tron, Ethereum, Bitcoin |
| TRC-20 / ERC-20 | มาตรฐานโทเคนบน Tron / Ethereum |
| Gas | ค่าธรรมเนียมเครือข่ายที่ผู้โอนจ่าย |
| Confirmation | จำนวนบล็อกที่ต่อหลังบล็อกที่มีธุรกรรม ยิ่งมากยิ่งมั่นใจว่าธุรกรรมไม่ถูกย้อน |
| Finality | จุดที่ธุรกรรมย้อนกลับไม่ได้แล้ว |
| Reorg | บล็อกล่าสุดถูกแทนที่ ทำให้ธุรกรรมที่เห็นแล้วหายไปได้ |
| EVM | เครือข่ายที่ใช้ระบบแบบเดียวกับ Ethereum เช่น BNB Chain ซึ่งใช้ address รูปแบบเดียวกัน |
| Self-custodial wallet | กระเป๋าที่ผู้ใช้ถือ key เอง ไม่ได้อยู่บน exchange |
| KYC / AML | การยืนยันตัวตน / การป้องกันการฟอกเงิน |
| Travel Rule | กฎที่ให้ข้อมูลผู้ส่งและผู้รับต้อง "เดินทาง" ไปพร้อมกับการโอน |
