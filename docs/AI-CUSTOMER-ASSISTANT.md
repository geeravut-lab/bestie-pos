# AI ผู้ช่วยลูกค้า (Customer-facing AI) — ออกแบบ

อัปเดต 18 พ.ย. 2569 · สถานะ: **ข้อเสนอออกแบบ รอเจ้าของยืนยันก่อนลงมือเขียนโค้ด**
เชื่อมกับ: `docs/AI-PROVIDER-MODEL-KNOWLEDGE.md`, `docs/AI-PROMPTS-RULES-KNOWLEDGE.md`, `docs/KARAOKE-AI.md`, งาน §13 ใน PHASE1_TASKS

## 1. หลักการที่ต้องไม่ผิด

1. **AI อ่านและอธิบาย โค้ดคำนวณและตัดสิน** (ข้อตัดสินใจเดิม 18 พ.ย.) ราคา โปรโมชั่น ความว่าง ข้อมูลภูมิแพ้ ข้อห้ามทางสุขภาพ ต้องมาจากฐานข้อมูลของร้านผ่านเครื่องมือ (tool call) ไม่ใช่ความจำของโมเดล
2. **"ไม่รู้" ไม่เท่ากับ "ปลอดภัย"** ถ้าลูกค้าขอ "ไม่มีหมู" แล้วเมนูไหนร้านยังไม่ได้ติ๊กข้อมูลวัตถุดิบ ระบบต้องไม่เสนอเมนูนั้นเป็นคำตอบที่ยืนยันแล้ว (แสดงเป็น "ยังไม่มีข้อมูล ถามพนักงาน")
3. **AI ให้ id ไม่ใช่ข้อความราคา** โมเดลตอบเป็น JSON `{message, suggestions:[{type,id,reason}]}` ฝั่ง server ตรวจว่า id มีอยู่จริงและเป็นของร้านนี้ แล้วหน้าจอวาดการ์ดจากข้อมูลจริง (ชื่อ รูป ราคา) โมเดลแต่งราคาหรือเมนูขึ้นเองไม่ได้
4. **ไม่ใช่คำแนะนำทางการแพทย์** (สปา/โยคะ) ไม่วินิจฉัย ไม่ให้ยา เจอสัญญาณเสี่ยงให้ส่งต่อคน
5. **ข้อมูลส่วนบุคคลน้อยที่สุด** (PDPA) ข้อมูลสุขภาพและรูปใบหน้าเป็นข้อมูลอ่อนไหว: ขอความยินยอมชัดเจน เก็บเท่าที่จำเป็น ลบอัตโนมัติ ไม่ใส่ใน log
6. **ข้อความจากร้าน/ลูกค้า/เมนูเป็น "ข้อมูล" ไม่ใช่คำสั่ง** (กัน prompt injection) โมเดลลูกค้าไม่มีเครื่องมือเขียนข้อมูลสำคัญเลย (ทำได้แค่ "ใส่ตะกร้าร่าง" และ "เรียกพนักงาน")
7. **ทุกหน้าจอมีปุ่ม "เรียกพนักงาน"** และ AI ล่มก็สั่งอาหาร/จองได้ตามปกติ (AI เป็นส่วนเสริม ไม่ใช่ทางเดียว)
8. **ควบคุมค่าใช้จ่าย:** โมเดลถูก (Haiku/Flash) เป็นค่าเริ่มต้น จำกัดจำนวนข้อความต่อโต๊ะ/ห้อง/เซสชัน มี usage log ต่องาน (งานค้างใน §13)
9. ครัว/บาร์ (KDS) ไม่มี AI (ตัดสินใจเดิม)

## 2. สถาปัตยกรรมร่วม

```
มือถือลูกค้า (หน้า /t/<token> หรือ /r/<room> หรือ /m/<member>)
   │  ข้อความ / เสียง→ข้อความ / รูป (ถ้ายินยอม)
   ▼
/api/guest/ai   (Vercel Function, ไม่ต้องมีบัญชี, ผูกกับ token ของโต๊ะ/ห้อง/นัดหมาย)
   │ 1) rate limit + งบต่อเซสชัน  2) โหลดบริบท: ร้าน ภาษา เมนู/บริการ (เฉพาะที่เปิดขาย)
   │ 3) เรียกโมเดลตามงาน (ai registry: provider/model/prompt แอดมินตั้งได้)
   │ 4) โมเดลเรียก "tools" (ฟังก์ชันอ่านอย่างเดียว) ผ่านโค้ดของเรา
   ▼
tools (SQL / core):  search_menu(filter) · get_item(id) · list_services() · find_slots(...) ·
                     check_treatment_rules(intake) · search_songs(q) · best_sellers(period)
   │ 5) โมเดลสรุปเป็น JSON → server ตรวจ id/schema → ส่งกลับ
   ▼
หน้าจอวาดการ์ดจากข้อมูลจริง + ปุ่ม "ใส่ตะกร้า / จอง / ขอเพลง / เรียกพนักงาน"
```

- **งาน (task) ใหม่ใน AI registry:** `guest.menu`, `guest.beauty`, `guest.wellness`, `guest.karaoke`, `guest.concierge`, `guest.stt` (เสียงเป็นข้อความ) — แต่ละงานเลือก provider/model/prompt ได้ที่หน้าแอดมินเดิม (`/ai`, `/admin/ai/prompts`) งานด้านความปลอดภัย (ตรวจเนื้อหา) ไม่มี fallback และแก้ไม่ได้ (เหมือนงาน safety เดิม)
- **โมดูล (registry):** `ai.guest` (พื้นฐาน, แผน Pro), `ai.guest.beauty`, `ai.guest.wellness`, `ai.guest.karaoke`, `ai.guest.concierge` — ปิดเป็นค่าเริ่มต้น เปิดต่อร้าน (ธรรมเนียม feature flag ข้อ 6 ของ CLAUDE.md) ร้านที่ไม่มีคีย์ AI เห็นหน้าจอปกติ
- **เสียง:** ใช้ Web Speech API ในเบราว์เซอร์เป็นอันดับแรก (ฟรี ไม่มีค่าเสียง แต่ภาษาไทยบน iOS Safari ยังไม่เสถียร) สำรองด้วย STT ฝั่ง server (อัปโหลดคลิปสั้น ≤ 15 วินาที ลบทิ้งหลังถอดความ) ต้องทดสอบภาษาไทย อังกฤษ รัสเซีย ฮีบรู เยอรมัน จีน (ภาษาของนักท่องเที่ยวเกาะพะงัน)
- **หน่วยความจำสนทนา:** เก็บแบบไม่ระบุตัวตนในเซสชัน 24 ชั่วโมง (ตาราง `guest_ai_sessions`) ผูกกับโต๊ะ/ห้อง ไม่ผูกกับตัวคน ยกเว้นลูกค้าที่ล็อกอินสมาชิกและกดยินยอม

## 3. กรณีใช้งานที่ผู้ใช้ขอ (A–D)

### A. ร้านอาหาร/คาเฟ่: "มีอะไรแนะนำ", "ไม่มีหมู", "ไม่เผ็ด"

**ข้อมูลที่ต้องเพิ่ม (ร้านเป็นคนตั้ง ไม่ใช่ AI เดา):**
- `menu_items.tags` : รายการแบบปิด (closed set) `contains_pork, contains_beef, contains_chicken, contains_seafood, contains_shellfish, contains_egg, contains_dairy, contains_gluten, contains_peanut, contains_tree_nut, contains_soy, contains_alcohol, vegetarian, vegan, halal` + `spice_level` 0–3 + `dietary_verified boolean` (เมนูนี้ร้านยืนยันแล้ว) + `highlight` (ร้านแนะนำ)
- ตัวช่วยกรอกในหน้าเมนู: ให้ AI **เสนอแท็กจากชื่อ/ส่วนผสม** แล้วเจ้าของกดยืนยันทีละเมนู (AI ช่วยร่าง คนเซ็น) ตัวเลือกเสริม (modifier) เช่น "ไม่ใส่หมูสับ" ก็มีแท็กของตัวเอง

**วิธีทำงาน (ถูกต้องและไม่หลอน):**
1. ลูกค้าพิมพ์/พูด "ขออาหารไม่มีหมู ไม่เผ็ด คนละไม่เกิน 250"
2. โมเดลแปลงเป็น **ตัวกรอง JSON** `{exclude:["contains_pork"], max_spice:0, max_price:25000, category:null}`
3. **SQL** กรองจากแท็ก ไม่ใช่โมเดล เมนูที่ `dietary_verified=false` และแท็กที่ถามยังไม่รู้ จะถูกแยกไปกลุ่ม "ยังไม่ยืนยัน ถามพนักงาน"
4. โมเดลจัดอันดับ/เขียนเหตุผลสั้น ๆ จากผลที่ได้ ("เมนูนี้ร้านระบุว่าไม่มีหมูและเผ็ดน้อย") + แนบข้อความเตือนมาตรฐาน **"ตามข้อมูลที่ร้านระบุ ถ้าแพ้อาหารรุนแรงกรุณาแจ้งพนักงาน"**
5. "แนะนำอะไรดี": ใช้ `best_sellers` (SQL จากรายงานจริง) + `highlight` ของร้าน + ความเข้ากับคำถาม (เช่น "ของหวาน", "กินกับเบียร์")
6. ปุ่ม "ใส่ตะกร้า" ใช้ตะกร้าและขั้นตอนสั่งเดิมของหน้า QR (ตัวเลือกบังคับยังตรวจที่ฐานข้อมูล)

**ทดสอบก่อนเปิดใช้:** ชุดคำถามทองคำต่อภาษา เช่น 50 คำถาม "ไม่มีหมู/ไม่มีถั่ว/มังสวิรัติ/ฮาลาล" ต้อง **ไม่ปล่อยเมนูที่มีแท็กต้องห้ามหลุดเลย (recall = 100%)** และทุกเมนูที่ตอบต้องมี `dietary_verified=true` หรืออยู่กลุ่ม "ยังไม่ยืนยัน"

### B. ร้านทำผม: แนะนำทรงผม

**ข้อมูล:** `style_catalog` (ทรงผมของร้าน: รูปผลงานช่าง แท็กความยาว/ลอน/สี/ดูแลง่ายยาก/เหมาะรูปหน้า/เหมาะผมแบบไหน, บริการและเวลาที่ต้องใช้, ราคา, ช่างที่ทำได้)
**ขั้นตอน:**
1. ถาม 4–6 ข้อ: ลักษณะผมปัจจุบัน (เส้นผม ความยาว เคยทำสี/ยืด), ไลฟ์สไตล์ (ดูแลได้กี่นาที/วัน), โอกาส (ทำงาน เที่ยว งานแต่ง), งบและเวลา, ข้อจำกัด (ผมบาง แพ้สีย้อม)
2. **รูปถ่าย (ไม่บังคับ):** ลูกค้ากดยินยอมก่อน → โมเดลที่รับภาพประเมินรูปหน้า/ลักษณะผมเพื่อกรอง "ทรงที่เหมาะ" จากแคตตาล็อกของร้าน เก็บรูปไม่เกิน 24 ชั่วโมงหรือจนจบเซสชัน ไม่ใช้ฝึกโมเดล ไม่ตัดสินเรื่องเชื้อชาติ/อายุ/เพศ
3. ตอบเป็น 3 ทรงจาก **แคตตาล็อกของร้านเท่านั้น** + เหตุผล + ช่างที่ทำได้ + เวลา/ราคาจริง + ปุ่ม "จองช่าง/เวลาว่าง" (ใช้โมดูล appointments เฟส 2)
4. ภายหลัง (เฟสถัดไป): ลองทรงบนรูปตัวเอง (virtual try-on) ด้วยโมเดลสร้างภาพ ต้องมีป้าย "ภาพจำลอง ผลจริงอาจต่าง" และขอความยินยอมแยกอีกครั้ง

### C. สปา/โยคะ: แนะนำโปรแกรมตามอาการและข้อจำกัด

**หลัก:** ใช้ **กฎที่ร้าน/นักบำบัดเซ็นรับรอง** กรองโปรแกรม โมเดลมีหน้าที่ถามให้ครบและอธิบาย ไม่ใช่ตัดสินความปลอดภัยเอง

**ข้อมูล:** `treatments` (นวดไทย น้ำมัน ประคบ ฝังเข็ม โยคะ ฯลฯ) มี `intensity` 1–5, `area_tags`, `benefits`, `contraindications[]` (เช่น `pregnancy_t1`, `recent_surgery`, `hypertension_uncontrolled`, `blood_thinners`, `skin_infection`, `fever`, `varicose_veins`, `osteoporosis_severe`, `essential_oil_allergy`), `needs_therapist_review boolean`

**คำถามคัดกรอง (ถามเป็นขั้น ภาษาลูกค้า ตอบด้วยปุ่มได้):**
1. ต้องการอะไร: ผ่อนคลาย / ปวดเมื่อย (บริเวณไหน) / ฟื้นฟูหลังออกกำลัง / นอนไม่หลับ / อื่น ๆ
2. ระดับความปวด 0–10 เป็นมานานเท่าไร มีอาการชา ร้าวลงแขนขา อ่อนแรง หรือไม่ (**ธงแดง**)
3. อุบัติเหตุ/ผ่าตัด/กระดูกหักใน 6 เดือน, ตั้งครรภ์ (กี่สัปดาห์), ความดันสูง/โรคหัวใจ, เบาหวาน, ยาละลายลิ่มเลือด/ยาที่ใช้ประจำ
4. ผิวหนัง: แผล ผื่น ติดเชื้อ แพ้น้ำมัน/สมุนไพร/ลาเท็กซ์
5. ข้อจำกัดการเคลื่อนไหว: นอนคว่ำไม่ได้ ลุกนั่งลำบาก ใช้เครื่องช่วยเดิน
6. แรงกดที่ชอบ เวลาที่มี ผู้ให้บริการเพศใดที่สบายใจ

**ตรรกะ (โค้ด ไม่ใช่โมเดล):** `check_treatment_rules(intake)` คืน {รายการเหมาะ, รายการต้องให้นักบำบัดตรวจก่อน, รายการไม่แนะนำ + เหตุผล}
- **ธงแดง** (ชา/ร้าวลงแขนขา อ่อนแรง เจ็บหน้าอก ไข้สูง ตั้งครรภ์ไตรมาสแรก ผ่าตัดใหม่ ฯลฯ) → หยุดแนะนำโปรแกรมหนัก แสดงข้อความ "ควรปรึกษาแพทย์/แจ้งนักบำบัดก่อน" และปุ่มเรียกพนักงาน
- ผลสุดท้ายแนบ **ใบสรุปให้นักบำบัด** (คำตอบ + ข้อควรระวัง) ผูกกับการจอง ลูกค้ายืนยัน/เซ็นในแบบฟอร์ม intake (e-sign) ที่โมดูล spa เฟส 2 อยู่แล้ว
- ข้อความบังคับ: "นี่ไม่ใช่คำแนะนำทางการแพทย์ นักบำบัดจะประเมินอีกครั้งก่อนเริ่ม"

**ข้อมูลสุขภาพ = ข้อมูลอ่อนไหวตาม PDPA:** ขอความยินยอมชัดเจนก่อนเริ่มคำถาม, เก็บเฉพาะที่จำเป็น, เข้ารหัส/จำกัดสิทธิ์ (เฉพาะนักบำบัดที่รับงานนั้น), ลบอัตโนมัติใน 30 วันถ้าไม่ได้จอง, ไม่ส่งข้อความสุขภาพเข้า log/usage log (บันทึกแค่จำนวน token)

## 4. AI ควรอยู่ตรงไหนอีกบ้าง (E) — แผนที่จุดสัมผัสทั้งหมด

คะแนน: คุณค่า (V) / ความเสี่ยง (R) / ความยาก (E) 1–5 · เฟสที่แนะนำ

| รีสอร์ต (QR ในห้อง) | concierge: สั่งอาหารเข้าห้อง จองสปา/ทัวร์ ถามเวลาเช็กเอาต์ ข้อมูลเกาะที่ร้านเตรียมไว้ | 5 | 2 | 3 | 5c |
| คาราโอเกะ (D) | ค้นเพลงด้วยเสียง ส่งเข้าคิว | 5 | 3 | 4 | 5c |
| ค้างบิล/จ่ายเงิน | ตอบ "จ่ายยังไง/ขอใบกำกับภาษี" (ชี้ขั้นตอน ไม่แตะเงิน) | 2 | 1 | 1 | 5c |
| ฟีดแบ็ก/ร้องเรียน | รับคำติชมตอนจบ (สั้น ๆ) → สรุปให้เจ้าของ, ถ้าร้ายแรงแจ้ง LINE ผู้จัดการทันที | 4 | 2 | 2 | 5b |
| คิวร้านคาเฟ่ | "คิวผมอีกกี่นาที" (คำนวณจากคิวจริง) | 2 | 1 | 1 | 5c |
| โอนเครดิตด้วย Crypto | ตอบคำถามขั้นตอน/ค่าธรรมเนียม/เครือข่าย **ห้ามให้คำแนะนำการลงทุนหรือชี้ว่าถูกกฎหมายแทนทนาย** | 2 | 4 | 2 | หลังทนายยืนยัน |

### 4.2 ฝั่งพนักงาน
| จุดสัมผัส | AI ช่วยอะไร | เฟส |
|---|---|---|
| "Ask my shop" (ผู้จัดการ/เจ้าของ) | ถามตัวเลขด้วยภาษาธรรมชาติ ตัวเลขมาจาก SQL เท่านั้น (ค้างในงาน §13) | 5a |
| เขียนคำอธิบายเมนู/ร่างแท็กอาหาร | ร่างให้ คนกดยืนยัน | **ก่อน** |
| สรุปกะ/ส่วนต่างเงินสด | อธิบายสาเหตุที่เป็นไปได้จากรายการ | 5b |
| เตือนเตรียมของ | คาดยอดตามวัน/ฤดูกาล/อากาศ (สถิติ ไม่ใช่เดา) | 5c |
| ตอบลูกค้าบนรีวิว/LINE | ร่างคำตอบ ให้คนส่ง | 5c |
| แปลบทสนทนาพนักงาน↔ลูกค้า (หน้าจอแปลสด) | ช่วยสื่อสารกับนักท่องเที่ยวภาษาที่ไม่รู้ | 5b |

### 4.3 สิ่งที่ **ไม่ควร** ใช้ AI
คำนวณเงิน ภาษี แต้ม Credit; ตัดสินความปลอดภัยด้านอาหารหรือสุขภาพโดยลำพัง; อนุมัติคืนเงิน/ยกเลิกบิล; ตัดสินใจ KYC/AML (ใช้กฎโค้ด + คนตรวจ); จอ KDS

## 6. ลำดับทำงานที่แนะนำ
- **5a (ได้ผลเร็ว ความเสี่ยงต่ำ):** แท็กอาหาร + ตัวช่วย AI ร่างแท็ก + แปลเมนู → ผู้ช่วยเมนูในหน้า QR → "Ask my shop"
- **5b:** concierge พื้นฐาน, ฟีดแบ็ก, ทรงผม (หลังโมดูล appointments), สปา/โยคะ (หลังกฎผ่านการตรวจโดยนักบำบัด/ทนาย)
- **5c:** คาราโอเกะ, ทัวร์/เช่ารถ, รีสอร์ต concierge
- ทุกเฟส: ชุดทดสอบทองคำต่อภาษา, red-team (prompt injection ในชื่อเมนู/โน้ต), วัดต้นทุนต่อเซสชัน (เป้า < 1 บาท/เซสชันด้วยโมเดลถูก), ปิดโมดูลได้ทันทีต่อร้าน

## 7. คำถามที่ต้องให้เจ้าของตัดสินใจ
1. ใครจ่ายค่า AI ของลูกค้า: คีย์กลางของ Bestie (คิดค่าบริการแผน Pro) หรือร้านใส่คีย์เอง?
2. สปา/โยคะ: มีนักบำบัดหรือผู้เชี่ยวชาญที่จะเซ็นกฎข้อห้ามให้ร้านนำร่องหรือไม่ (ต้องมีก่อนเปิดใช้)
3. ภาษาที่ต้องรองรับก่อน (EN/TH ก่อน แล้ว RU/HE/DE/ZH?)
4. ทรงผม: จะให้เริ่มจากแคตตาล็อกอย่างเดียว หรือรวมรูปถ่ายลูกค้าตั้งแต่แรก
5. ข้อความ "ไม่แน่ใจ" ของ AI ให้เรียกพนักงานอัตโนมัติหรือแค่แนะนำให้กดเอง

**คำตอบของเจ้าของ (2026-11-19):** 1) ใช้คีย์กลางของ Bestie และคิดค่าบริการรวมในแผน Pro · 2) มีนักบำบัด/ผู้เชี่ยวชาญที่จะเซ็นกฎข้อห้ามให้ร้านนำร่อง · 3) EN/TH ก่อน แล้ว RU/HE/DE/ZH · 4) ทรงผม: เริ่มจากแคตตาล็อก และรวมรูปถ่ายลูกค้าตั้งแต่แรก (ต้องขอความยินยอมชัดเจน เก็บน้อยที่สุด ลบอัตโนมัติ — คำตอบยังกำกวม ยืนยันอีกครั้งก่อนสร้าง) · 5) เมื่อ AI ไม่แน่ใจ ให้แนะนำให้ลูกค้ากดเรียกพนักงานเอง
