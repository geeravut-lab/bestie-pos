A manager can set PINs but never an owner's, and can never invite an owner.

A required group with fewer options than its minimum is allowed to exist while the owner sets it up, but the editor shows a warning because the cashier could not finish that line.

- 2026-11-18 — **Offline-first = IndexedDB (Dexie) + an outbox** (`packages/offline`, rules in `packages/core/src/outbox.ts`). Every write is stored locally first with a client-made uuid and replayed in strict order; a network/server failure stops the run and retries with backoff (2 s → 5 min, ±20 %), a refusal (permission / constraint / "update touched no row") marks only that entry *dead* (kept, visible, retry/discard by a person) and the queue goes on, a duplicate-key answer to a replayed insert counts as done. Conflict rule per table: `insert-once` (orders, lines), `last-write-wins` (menu), `server-wins` (payments, Credit and Points ledgers — the device asks through an RPC and takes the answer; unknown tables default to server-wins). Reads are network-first with the last good copy as fallback (`cachedRead`), including the signed-in user's shop data, so the app opens with no signal. Sign-out clears caches and remembered PINs but never the unsent queue.
- 2026-11-18 — **Till identity**: the tablet signs in once with its own account — create it by inviting a person with the *device's* role (Cashier / Waiter / Kitchen), **not** an owner account, because the database only knows the signed-in account and applies its rights. People then identify with their PIN; the screen shows *their* role and permissions (never more than the account has), and a till locks itself after 5 minutes idle or by the Lock button. Offline, the tablet checks the PIN against a salted PBKDF2 verifier it stored the last time the server accepted that PIN here (5 wrong tries lock it 15 min); a person the server never accepted on this tablet needs signal once. This is a convenience for "who is acting", not a security boundary — whoever holds the signed-in tablet holds its session. Manager-only actions on a cashier tablet (void, refund, price override) will go through server RPCs that verify the manager's PIN, never through the browser's own permission list. If nobody has a PIN yet the till lets the account through so the owner can reach the Team page.

- 2026-11-18 — **Orders**: one order = one document on the tablet (`OrderDoc`) saved in IndexedDB together with the server writes it needs (one local transaction), then replayed in order. Order number = *device code* + running number of the Bangkok business day (A001, B001 …); the code is a letter assigned per device in a shop, so tablets that are offline together never clash. A repeated number is NOT swallowed as "already done": only a primary-key repeat counts as applied; any other unique conflict becomes a visible dead letter. Order status is `open` until the payment function closes it (`paid`); a plain client update cannot mark an order paid, and a closed order accepts no change. Lines freeze once sent (price, quantity, name, options); only their kitchen status moves forward; cancelling a sent line needs `order.void` and is a *critical* audit event; unsent lines are simply removed (kept as `void` rows so a queued copy can be closed too). Service charge applies to dine-in orders only; takeaway / delivery / QR-pickup carry none. A tablet must be set up as a device before it can open orders. The shop's orders are pulled into the tablet only when nothing is waiting to be sent, so an unsent change is never overwritten.
- 2026-11-18 — **Manager override on a cashier tablet** is still open: today a cashier account cannot cancel a sent line (the screen hides the button for people without `order.void`, and the database refuses it). The planned server function verifies a manager's PIN for one action; it arrives with split bill / shifts.
- 2026-11-18 — **Manager override (built)**: `void_line_with_manager` — a cashier asks, a manager types their PIN, the server checks it with the same lock-out rules as the lock screen (5 wrong tries lock it 15 minutes), checks that the approver's role really has `order.void`, cancels that ONE sent line, and the audit event records `approved_by`. A wrong PIN is an **answer (`ok:false`), not an exception**, because raising would roll back the failed-attempt counter and the lock-out would never trigger (found by a test). Online only; nothing stays unlocked on the tablet. `void_approvers` lists only managers who have a PIN. Price override and refunds will use the same pattern when those features exist.

- 2026-11-18 — **Closing a bill and receipts**: a bill is closed only by the server function `close_order()` (never a plain update). The till may call it offline: it is queued after the order's own writes and replayed; sending the same close twice is a no-op. The function checks permission (`payment.take`), that the lines it closes add up to the subtotal the till showed (otherwise the bill changed elsewhere and a person must look), the device's receipt series, the arithmetic of totals and rounding (≤ 1 baht), and that cash payments cover the amount due. **Only cash can be closed from the till**; PromptPay / card are confirmed by the Stripe webhook and Credit / Points by server-side ledgers, so a tablet can never declare them paid. A **receipt** is a frozen snapshot — seller name and tax ID (from the legal entity), branch, POS ID of the device, VAT / service rates, totals, rounding, payments — filled by the server from its own records, never trusted from the till; later edits of the shop or menu do not change it. Receipt numbers are per device and consecutive (`A-000001`), kept in a counter that survives sign-out and is raised to the server's highest number when online; a repeat is refused by the database. Cash rounding is its own line (the shop's rule from Billing); change is computed on the rounded amount. Receipts and payments are history: they cannot be edited or deleted.
- 2026-11-18 — **Outbox ordering**: every queued write gets a timestamp strictly after the last one (two saves in the same millisecond, or a clock that steps back, can no longer swap their order).

- 2026-11-18 — **Online payments (Stripe)**: the till asks (`begin_payment_attempt`: permission, bill = lines, exact amount, no cash rounding), the server creates the Stripe PaymentIntent, and **only the signed webhook `payment_intent.succeeded` closes the bill** (`confirm_payment_attempt`, service role only). Every confirmation re-checks amount, currency and that the bill is still open and unchanged; anything else becomes `needs_review` (money may have moved) and is never silently closed or dropped. Webhook answers: 400 bad signature, 200 handled / ignored, 500 not processed (Stripe retries; the database functions are safe to repeat). Cards use **server-driven Stripe Terminal** (the server hands a `card_present` intent to the device's registered reader `tmr_…`) — no Terminal SDK in the browser, no card data in Bestie. PromptPay shows Stripe's QR image; the till polls the attempt every 2 s and an unfinished attempt can be shown again after a refresh. Cancelling stops the reader and cancels the intent; a payment that arrives anyway still closes the bill. Before an online payment the till sends anything unsent to the kitchen and flushes its queue so the server sees the bill exactly as shown.
- 2026-11-18 — **Two receipt series per device**: the till numbers its offline cash receipts `A-000001…` (device-local, consecutive); receipts of server-confirmed payments are numbered by the server in `A+000001…` (consecutive, gap-free because a failed attempt never consumes a number). Each series is consecutive on its own. **Accountant to confirm** that two series per POS device are acceptable for abbreviated tax invoices; if not, online payments move to the same series by making the till fetch the number from the server before starting (online only).
- 2026-11-18 — **To verify with a Stripe test key (could not be run from the build environment)**: (1) PromptPay PaymentIntent needs `billing_details.email` — a neutral `pos-<id>@<our host>` address is used and no receipt e-mail is requested; (2) PromptPay `next_action.promptpay_display_qr_code.image_url_png` is shown to the guest; (3) `terminal/readers/{id}/process_payment_intent` works for the shop's reader model in Thailand; (4) Thai accounts accept `currency=thb` for `card_present`. Test-mode checklist is in docs/ENVIRONMENT.md.

- 2026-11-18 — **Split and merge** are done by *moving lines between bills*, never by paying part of a bill: every bill still closes with one `close_order` and one receipt. A sent line's quantity is frozen for everyone except `move_order_lines()` (a privileged server function that checks `order.create`, shop, open bills and is safe to replay); part of a line that is moved becomes a new line with the same price, state and sent time, so the kitchen history and the money do not change. A merged-away bill is closed as `void` with a note (it is not a sale). The till queues only the new bill's header and the one move call. **Split by equal amount / partial payments belong to split tender** (several payments on one bill) and are not built yet.
- 2026-11-18 — **Shifts**: one open shift per device (database-enforced). The till computes the expected drawer cash instantly (opening cash + cash receipts of its own series in the shift window) and the server recomputes it from confirmed cash payments of that device when the shift closes — the stored variance is the server's number. PromptPay / card are shown in the summary but never counted in the drawer. `stores.shift_required` (default off) makes the till refuse payments until a shift is open. A shift left open across devices or days is a manager's job to close; there is no automatic close yet.

- 2026-11-18 — **Kitchen display**: a kitchen / bar screen signs in with a Kitchen account that has only `kds.use` (it cannot take orders or edit anything). It reads the shop's bills like every tablet (store topic ping + a 10 s pull) and changes lines only through `set_lines_status()`: sent → ready → served, with a one-step undo for a mis-tap; price, quantity and name stay frozen. A line reaches a screen by its **station** (the menu item's setting at the time it was ordered); lines without a station never appear on any screen; a KDS device with no station (expo) shows every line that has one. Colour by waiting time: 8 min amber, 15 min red. Bumps are saved on the screen and queued like any other write, so a short outage does not lose them — but **new tickets only reach the screen while it has network** (no LAN link between tablets yet; the screen says so when offline). Waiters mark served from the Ready list; the cafe queue (counter bills only) shows Preparing / Ready and a customer-facing call screen.

- 2026-11-18 — **Reports**: every number comes from one read-only database function `sales_report(p jsonb)` over the frozen history (paid orders joined to their receipts, confirmed payments, non-cancelled lines), by Bangkok business date, for one shop or every shop the person may open; it needs `report.view`, refuses ranges over 366 days and returns one jsonb document, so the screen, the CSV files and (later) "Ask my shop" read the same figures. Void bills and cancelled lines never count. Items are grouped by Thai name. CSV amounts are plain baht decimals (spreadsheet-friendly) with the formula-injection guard; each export writes the critical audit event `export.report`.

- 2026-11-18 — **Demo data is a server function, not a seed file**: `seed_demo_menu(store)` fills an EMPTY restaurant / cafe shop of the caller (needs `menu.edit`; refuses any shop that already has categories or items), so a demo or pilot shop starts from realistic Thai / English data and the same guards as hand-typed rows apply. Nothing is ever overwritten. Pilot onboarding steps live in docs/PILOT-CHECKLIST.md.

- 2026-11-18 — **Guest QR ordering**: the QR on a table holds a random 128-bit token (`dining_tables.qr_token`); the token is the only key a guest has, and a phone talks to the database only through server functions with the service role (`/api/guest/menu`, `/api/guest/order` → `guest_table / guest_menu / guest_bill / guest_place_order`, executable by `service_role` only). The database computes prices (dine-in channel), checks that every option belongs to the dish and obeys min / max, that the dish is available, and that the `order.qr` module is on (a SQL copy of the registry entry, kept honest by `guestSql.test.ts`); the phone sends ids, quantities, option ids and a note — never prices. A guest bill is an ordinary dine-in bill on the table (numbers `QR001…`, two letters so they never clash with a device's single letter), so splitting, kitchen screens, payment and reports work unchanged. Default: guest lines arrive as **unsent** lines for staff to send (shop setting `qr_auto_send` sends them straight to the kitchen); a pilot shop should choose. Abuse limits: ≤ 30 lines per order, ≤ 150 per bill, 12 orders per table per 10 min, per-phone rate limit in the function, a replayed `client_id` returns the first answer. Staff can replace a table's code at any time (`rotate_table_qr`). Table prices for the `qr` channel are not used yet (all table orders are dine-in). **Pay at the table (PromptPay) is the next PR** — it needs a device for the receipt series.

- 2026-11-18 — **Pay at the table (guest PromptPay)**: same machinery as the till — a payment *attempt*, a Stripe PromptPay QR, and only the signed webhook closes the bill. The handler computes the bill itself (`computeBill` from packages/core, imported by relative `.js` path; a test proves the snapshot equals the till's `onlineSnapshot`), so the phone can never name an amount. Receipts of guest payments need a POS device for the numbering series and POS ID: `stores.qr_pay_device` (owner's choice in Billing & points, NULL = off; the accountant should confirm which device). Guard rails: no payment while any line is still waiting for staff (`new`), no new orders while a QR is waiting (`55006` → "bill locked"), one live attempt per bill (a reload resumes it, a changed amount cancels it at Stripe and starts anew), the guest can cancel, status is readable only with the table's token. Guest payment cannot split the bill or add a tip yet. **Not verified against real Stripe from the build sandbox** — run the test-mode checklist.

- 2026-11-18 — **Customers and the Points ledger**: a customer belongs to an org (one legal entity for now); found by phone digits, member code or name through `find_customers`, created through `create_customer` (a repeated phone is refused so the existing member is used). Writes go through functions only. `points_ledger` is append-only (a trigger refuses update / delete), kinds are a closed set enforced by CHECK (no purchase / cash-out / transfer), signs are enforced per kind, and `earn` / `redeem` are unique per bill so a replayed close can never earn twice. Points are earned inside `finalize_order_payment` (the one place every bill is closed): floor(eligible spend ÷ the org's earn step); eligible = cash + PromptPay + card, plus Credit when the org's rule says so; never the Points portion, never from buying Credit. The balance is always the ledger's sum, never a stored number. Manual corrections need `credit.adjust` (owner today), a reason, never below zero, critical audit event `points.adjust`. Choosing a customer on a bill is an online action (`set_order_customer`) — selling never depends on it. **Redeeming points as a discount** (and Credit) are the next PRs; the open accounting point is that a Points discount lowers the VAT base, which the accountant should confirm.

- 2026-11-18 — **Bestie Credit ledger**: a separate `credit_ledger` (never mixed with Points), append-only, THB 1:1 in satang, every row one balanced posting (top-up: debit `cash` / `psp_clearing`, credit `customer_credit`; spend: debit `customer_credit`, credit `sales`; corrections through `adjustment`). A balance is always read per (customer, **legal entity**): Credit issued by one company can never be spent at another company's shop because the other entity's balance is simply zero — the single-entity rule lives in the data, not in the UI. The ledger has no cash-out kind and no crypto funding value (CHECK constraints + a test that reads the migration), a balance cannot go below zero (trigger), top-ups are 100–50,000 THB each and a balance is capped at 200,000 THB (e-money safety margin, owner/lawyer may change). `tender.credit` is off for every profile; the owner switches it on per shop (`credit_enabled()` is a SQL copy of the registry entry, mirrored by a test). Cash top-ups count in the drawer: `close_shift` adds the top-ups taken on that device (the till's instant local estimate does not include them; the server's number is the stored one). `credit_liability` reports what each company owes its customers (deferred revenue). **Still needs the lawyer's confirmation before real customers hold Credit** (Open questions).

- 2026-11-18 — **Split tender** (cash + Bestie Credit, any number of payers): one server function `close_order_tenders` closes the bill in one transaction — receipt, payments, one balanced Credit spend posting, Points earned — and numbers the receipt in the device's server `+` series (so a split closing is online-only; the till's offline `-` series stays for single cash payments). Rules checked in the database: legs add up exactly to the amount due, cash legs carry tendered / change, a Credit leg needs a customer on the bill, the Credit module on, and a balance in the shop's own legal entity; unsent lines are refused (`55000`); the same request again returns the first receipt (first payment id is the key). The shop's cash rounding applies to the cash portion only; the till (core `planSplit`) carries the difference on the last cash leg. Equal shares use the penny-exact `splitEvenly`. PromptPay / card legs are NOT mixed in yet (they are a whole-bill payment through the provider). Points are not a tender: they will be a bill discount.

- 2026-11-18 — **Crypto top-up (built from docs/CRYPTO_TRANSFER_KNOWLEDGE.md, off by default)**: crypto only ever becomes **Bestie Credit** (THB 1:1 at the rate locked in the request); it is never a way to pay a bill and Credit has no cash-out, so crypto-funded Credit can never leave as cash. The module works only when ALL of these hold, checked in SQL on every function: the shop switched `credit.topup.crypto` on, Credit is on, and the org record has `legal_sign_off.cryptoTopup = true` (withdrawing the sign-off stops the functions at once). v1 = **USDT on Tron and on Ethereum**. A **payment request** locks the rate for 15 minutes (the LOWER of two public sources that agree within 1.5 %; otherwise no request) and asks for an exact USDT amount made unique with a suffix of 1–999 micro-units; the chain watcher matches by wallet + amount (tolerance 0.5 % or 0.10 USDT, whichever is smaller; two near-identical candidates = a person decides) and Credit is added only when the transfer is **final** (Tron 20 blocks via the solidity node, Ethereum 12) and the sender is not blocklisted; the ledger id **is** the request id, so nothing is credited twice. Everything unusual (under / over / late / unmatched / ambiguous / blocked / T2 sender not proven) goes to a review queue for `credit.adjust`; a reviewer can credit only what was actually received, at the locked rate, never more than the request. KYC: T1 / T2 with the knowledge file's limits (waiting for the lawyer), records never edited or deleted, readable only with `credit.adjust`; T2 needs the owner. A company wallet is a PUBLIC watch-only address; changing it needs **two different people**; no private key exists anywhere. The spec's "rate locked at confirmation" (product spec §6) is implemented as **locked at the request and stored with the confirmation**, as in the knowledge file. Exchange / payment-processor APIs of Thai licensed operators are never used (prices only). Known gaps: BTC / USDC / other chains, automatic signed-message checks, Tron / Ethereum / price-source response shapes **not run against live services from the sandbox** (marked in code), Vercel Cron not enabled (needs a Pro plan or an external scheduler).
