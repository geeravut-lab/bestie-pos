- 2026-11-17 — Core money rules (packages/core): money = integer satang; basis points for rates; rounding is per tender (`RoundingRule`, default exact) and shown as its own bill line; bill order = line discounts → bill discount → Points discount (capped) → service charge on the discounted subtotal → VAT on (subtotal + service). Service charge carries VAT. **Accountant must confirm** (Open questions).
- 2026-11-17 — Points: earned only from confirmed cash / PromptPay / gateway / **Credit-spend** payments (never on the Points portion, never from buying Credit); redeemed only as a bill discount capped by `maxRedeemBps`; ledger kinds are a closed set and unknown kinds such as `purchase` / `cash_out` are rejected at runtime. Defaults (editable per org): 1 point per THB 25, 1 point = THB 1, max 50 % of a bill.
- 2026-11-17 — Modules: `tender.credit` is off by default for every profile until the lawyer confirms the single-entity prepaid structure; `credit.topup.crypto` depends on it and needs `legalSignOff.cryptoTopup`. `deposits` depends on `appointments` (a table reservation is an appointment). Plan tiers are cumulative: basic ⊂ pro ⊂ resort.

- 2026-11-17 — SSO accounts always use a **synthetic** address `aivora+<hub id>@<site host>` (the hub's e-mail is stored only as `user_metadata.hub_email`). Deviation from docs/SSO-Aivora-Supabase.md ("use the hub e-mail if present"): the hub does not say whether its e-mail is verified, so creating a confirmed account with it would let someone pre-register another person's e-mail (account squatting). Linking is by hub user id in `aivora_links`.
- 2026-11-17 — Login never assigns a role. A new user (e-mail, Google or LINE) lands on shop onboarding; `create_org()` makes them the owner of the shop they create. Staff are added to an org by an owner/manager. Platform admin = row in `platform_admins` (service_role only).

- 2026-11-17 — Audit trail: the org owner/admin can switch auditing off and untick event types (stored as "only what is off"). **35 event types; 14 are `critical`** (refund, void, Credit/Points ledger changes, staff role/deactivation, POS ID, module toggles, legal sign-off, audit settings, audit export, password change) and are always recorded — the switches cannot hide them. Proposal from KNOWLEDGE-MAPPING §A, implemented; the owner may change the list of critical events.

- 2026-11-18 — Security: Supabase grants EXECUTE on new functions to `anon`/`authenticated` by default, which left internal SECURITY DEFINER functions (e.g. `audit_record`, `live_ping`) callable from the browser with only the public anon key (anyone could have written audit events). Found with the Supabase security advisor right after the first deploys; fixed by migration 8 (applied) with tests; new functions now get no grants by default. No data had been written through this path (the project had no users yet).

- 2026-11-18 — Billing & points are **owner-selectable options**, not constants: per store — VAT registered / rate, service charge %, menu prices incl./excl. VAT, service charge taxable or not, computed before or after discounts, cash rounding (none / 25 / 50 satang / baht / floor); per org — Points rule (baht per point, value per point, max % of a bill, whether Credit spend earns points). Stored as data (`stores.bill_options`, `stores.rounding`, `orgs.points_rule`), shape-guarded in the database, audited as `settings.change`, previewed live on a sample bill. The ban on buying / cashing out points is deliberately not an option.

- 2026-11-18 — **Payment gateway / PSP = Stripe** (owner decision): cards and Thai **PromptPay QR** through Stripe PaymentIntents; the signed webhook (`payment_intent.succeeded`, secret `STRIPE_WEBHOOK_SECRET`) is what confirms a payment and auto-closes the bill — the cashier's screen never decides "paid" by itself. Code sits behind a gateway interface so another provider can be swapped in. Keys are server-only Vercel env vars (already set). This answers the open questions "which PSP / bank API confirms PromptPay" and "payment gateway choice"; the *acquirer for physical card terminals* stays open.
- 2026-11-18 — **Stripe Terminal is in Phase 1** (owner decision): shops can take in-person card payments with a Stripe Terminal reader as well as PromptPay QR and online card. The reader flow goes through the same gateway interface and the same signed webhook, so a card tap and a QR payment close a bill the same way. Reader model and country availability still to confirm with Stripe (hardware list, Open questions).
- 2026-11-18 — Auth e-mail: the owner configured SMTP (Resend) inside Supabase Auth and removed the `RESEND_*` / `EMAIL_*` variables from Vercel. The app never sends auth e-mail itself.
- 2026-11-18 — **Shop devices and staff PIN model.** A shop tablet is signed in once with an org account (owner / manager sets it up; it is registered in `devices` with a role and, for KDS, a station). Staff then identify themselves on that tablet with a **PIN** (4–8 digits, bcrypt in `staff_pins`, never readable by the browser; 5 wrong tries lock that PIN for 15 min and write `auth.pin_lockout`). The PIN only selects *who is acting* for audit and permissions; money-moving actions are still checked on the server against that person's role. A manager can set PINs but never an owner's, and can never invite an owner.
- 2026-11-18 — **Staff invites** replace e-mail invitations: owner/manager creates a 12-hex-digit code (shown once, only its SHA-256 is stored, valid 7 days, single use, optional single-shop scope). The invitee signs up or signs in by any method (e-mail, Google, LINE) and redeems it on the first screen (`accept_staff_invite`), so SSO identities can be staff without ever receiving a role from SSO.
- 2026-11-18 — **Adding a shop** (`create_store`) always reuses the org's first legal entity (or a chosen one of the same org) — Bestie Credit is scoped to the legal entity, so a second company is a separate org, not a second shop. Phase 1 offers Restaurant and Cafe profiles only.
- 2026-11-18 — The module toggle screen saves only the difference from the profile default (`module_overrides`) and the database refuses unknown module ids, non-boolean values and `credit.topup.crypto` without `orgs.legal_sign_off.cryptoTopup`.

- 2026-11-18 — **Menu data model**: one menu per shop (rows carry `org_id` + `store_id`); categories → items; add-on option groups (min/max) → options, linked to items by `modifier_group_ids`. Prices are integer satang in `prices` jsonb `{base, dine-in?, takeaway?, delivery?, qr?}` (only differences from base are stored); an option's `price_delta` may be negative and may be overridden per channel. Names are `{th (required), en?}`. Rows are soft-deleted (`deleted_at`) so order history and offline replays keep working; old orders keep a snapshot of name and price. A required group with fewer options than its minimum is allowed to exist while the owner sets it up, but the editor shows a warning because the cashier could not finish that line.

- 2026-11-18 — **Offline-first = IndexedDB (Dexie) + an outbox** (`packages/offline`, rules in `packages/core/src/outbox.ts`). Every write is stored locally first with a client-made uuid and replayed in strict order; a network/server failure stops the run and retries with backoff (2 s → 5 min, ±20 %), a refusal (permission / constraint / "update touched no row") marks only that entry *dead* (kept, visible, retry/discard by a person) and the queue goes on, a duplicate-key answer to a replayed insert counts as done. Conflict rule per table: `insert-once` (orders, lines), `last-write-wins` (menu), `server-wins` (payments, Credit and Points ledgers — the device asks through an RPC and takes the answer; unknown tables default to server-wins). Reads are network-first with the last good copy as fallback (`cachedRead`), including the signed-in user's shop data, so the app opens with no signal. Sign-out clears caches and remembered PINs but never the unsent queue.
- 2026-11-18 — **Till identity**: the tablet signs in once with its own account — create it by inviting a person with the *device's* role (Cashier / Waiter / Kitchen), **not** an owner account, because the database only knows the signed-in account and applies its rights. People then identify with their PIN; the screen shows *their* role and permissions (never more than the account has), and a till locks itself after 5 minutes idle or by the Lock button. Offline, the tablet checks the PIN against a salted PBKDF2 verifier it stored the last time the server accepted that PIN here (5 wrong tries lock it 15 min); a person the server never accepted on this tablet needs signal once. This is a convenience for "who is acting", not a security boundary — whoever holds the signed-in tablet holds its session. Manager-only actions on a cashier tablet (void, refund, price override) will go through server RPCs that verify the manager's PIN, never through the browser's own permission list. If nobody has a PIN yet the till lets the account through so the owner can reach the Team page.
